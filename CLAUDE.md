# CLAUDE.md

Instruções para o Claude Code ao trabalhar neste repositório.

## Sobre o projeto

**TurStar API**: API REST em Ruby on Rails (modo `api_only`) para uma agência de viagens.

- Ruby 3.2.9, Rails 8.0.4 e PostgreSQL 15. A atualização de versões está na issue #53.
- Autenticação com JWT (`app/controllers/concerns/Authentication.rb`) e autorização com Pundit (`app/policies/`).
- O app Rails fica em `src/`. O `Dockerfile` e o `docker-compose.yml` ficam na raiz.
- Rotas versionadas em `/api/v1/*` (`src/config/routes.rb`).

### Como rodar

```bash
cp .env.example .env            # definir JWT_SECRET=valor (sem espaços ao redor do =)
docker compose up --build -d
docker compose exec rails bin/rails db:create db:migrate db:seed
```

Sempre que o `Gemfile` mudar, é preciso reconstruir a imagem com `docker compose up --build -d`.

## Fluxo de resolução de issues (label `claude`)

O label **`claude`** marca as issues que a pessoa dona do repositório quer que o Claude resolva. O label funciona como uma **fila**: o Claude não é acionado automaticamente. Quando for chamado, por exemplo com "resolve as issues com label claude", ele deve processar as issues **abertas** com esse label.

### Para cada issue

1. **Ler a issue inteira**: descrição, sugestão, "Etapas para conclusão" e dependências (ex.: "Depende da #38"). Se uma dependência ainda estiver aberta, comentar isso na issue e pular para a próxima.
2. **Confirmar que o problema ainda existe** no código atual da `main`. Se já tiver sido corrigido, comentar explicando e não criar a branch.
3. **Criar uma branch nova a partir da `main` atualizada**, com uma branch por issue:
   - Padrão: `fix/issue-<número>-<resumo-curto>` para bugs e `feat/issue-<número>-<resumo-curto>` para melhorias.
   - Exemplo: `fix/issue-2-authorize-categoria`.
4. **Comentar na issue que o trabalho começou**, informando o nome da branch.
5. **Implementar apenas o escopo da issue.** Não corrigir outras issues "de carona". Se encontrar algo fora do escopo, mencionar no comentário final.
6. **Validar** da forma possível (testes, `bin/rails runner`, `curl`) e registrar o que foi e o que não foi validado.
7. **Commit e push da branch.**
   - Mensagem no padrão Conventional Commits em português, com `Closes #<número>` no corpo.
   - Exemplo: `fix: instancia categoria antes do authorize` + `Closes #2`.
8. **Comentar na issue o que foi feito** (ver o formato abaixo).
9. **Não abrir pull request.** A pessoa dona do repositório abre e revisa o PR. Deixar apenas a branch publicada.
10. **Não remover o label** nem fechar a issue. Ela fecha sozinha quando o PR com `Closes #N` for mergeado.

### Formato do comentário final na issue

A pessoa dona do repositório está **reaprendendo Rails**, então o comentário deve ser **didático**: além de dizer o que mudou, explicar o porquê, ligando ao conceito de Rails envolvido.

```markdown
## ✅ Implementado na branch `fix/issue-N-resumo`

### O que foi feito
- `caminho/do/arquivo.rb`: o que mudou

### Por que (conceito de Rails)
Explicação curta e simples do conceito envolvido (ex.: callbacks, associações, Pundit).

### Como validar
Passo a passo (comando ou curl) e o resultado esperado.

### Observações
O que não foi validado, riscos ou assuntos fora do escopo encontrados.

---
_Generated by [Claude Code](https://claude.ai/code)_
```

Todo comentário no GitHub deve terminar com o rodapé `_Generated by [Claude Code](https://claude.ai/code)_`.

## Convenções gerais

- Idioma de issues, comentários e commits: **português**.
- Não commitar segredos (`.env`, tokens, senhas reais).
- Não alterar a `main` diretamente. Todo trabalho vai em branch própria.
